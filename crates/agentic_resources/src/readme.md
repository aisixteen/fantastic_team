# agentic_resources — a registry of agent roles
Verbs: reflect, roles, role, spawn, fleet, set_limit, get_count.

**A role is a META BUNDLE**: fantastic's `bundles/<name>/bundle.yaml` with a `base` (an AI backend) and no program, its `record` carrying the directive (`post_system_prompt`, which the child gets AFTER fantastic's default system block: it keeps the primer with the call grammar, its identity and its grants) and the grants (`can_call`; the key `$registry` stands for this registry, or name it by id). A role names no model. The registry reads the roles from the kernel's bundles on every call (`reflect` with `bundles: all` lists the same bundles); a bundle that failed to load is listed in `roles` `errors`. No role is built in.

**Config is the record**: `limits` (kept by `set_limit`). A role is any kind of agent, not only code.

**The backend.** A child runs on its SPAWNER's backend (its compiled handler, through any bundle the spawner is, and its provider fields: `model`, `endpoint`, `credentials`, `memory_store_id`, …), with the `model` the spawn names (the spawner's own when none). The child is created as `bundle: <role>` on that handler: the kernel lays the role's fields under the spawn's.

**`spawn {role, model?, backend?, task?, name?, limits?}`** makes the agent as a CHILD OF THE CALLER and gives the caller `pause`, `resume` and `stop` on it (both ends of the grant), so a lead always controls its subtree. It also opens the edge child -> caller with `send` on both ends (the child's `can_call` and the caller's `callable_by`, each MERGED with what is already there, never overwritten): the child tells its parent with a plain `send`, and the message starts the parent's next turn like any message. A `task` string is sent to the child as its first message (any other `task` is `bad_arg`). Nothing is stored on any record. The task tree is `task_registry`'s, not this registry's.

**Tool grants.** The role's grants on tools are applied on BOTH ends of each edge: the child's own `can_call` and the tool's `callable_by`, so a spawned worker calls its tools with no setup in the directive text. A tool id that is not an agent is skipped (the child's grant stays). A role may only grant what its spawner itself holds (every listed verb in the spawner's own `can_call`, `"*"` only against `"*"`; `$registry` and the `$` tokens are not checked, and an operator spawn has no spawner to check), or the spawn is refused `not_allowed` with a reason naming the spawner, the verb and the tool, before anything is created or forked. If a grant cannot be written the whole spawn is undone and the reply is `grant_failed`. `delete_agent` of a spawned agent drops its entries from every tool's `callable_by`.

**`spawn {role, from:{agent, at}, task?, name?, limits?}`** branches the new agent off a fork point of an existing agent (`fork_points`, `mark`): the registry asks ai_core to `fork {at}` that agent, then applies the role (its directive and grants, `bundle: <role>`) and the limits like any spawn. The fork stays in the source's memory store (so its copied prefix is readable and the prompt cache is warm; another model starts cold), keeps the store grant and none of the source's other grants, and its `limits`, `role` and `spawned_by` are the new spawn's, never the source's (a `task` on the source record is dropped). Placement: the fork lands BESIDE its source (under the source's parent), not under the caller; the caller still gets `pause`, `resume` and `stop` on it, and the fork may `send` the caller. The caller must itself hold `fork` on `agent`, or the spawn is refused with reason `not_allowed`. The registry's limits are checked before anything is forked, and a refusal from fork (`no_such_row`, `cuts_turn`, `cuts_fold`, `parent_mid_turn`, `store_refused`, ...) passes through unchanged with nothing left behind. The record carries `lead` (the caller) so the fork counts against that lead's subtree quota though it sits beside its source. The reply is `{id, role, model}` plus `from:{agent, at}` and `copied` (the rows the fork carried over).

**Limits.** `set_limit {role?, max}` caps one role, or all agents in total; `max: null` clears. `get_count` counts EVERY agent this registry spawned that still exists; a slot frees only on `delete_agent`, never when a child says it is done. `spawn limits:{total?, per_role?}` hands a sub-lead part of the caller's quota; a subtree never exceeds what it was given. Counts are read off the records (`spawned_by`, `role`), so a delete lowers them and a restart rebuilds them.

**No cleanup.** A child's `send` only messages its parent: nothing is retired or deleted. `delete_agent` is the only way out.

**Refusals** are the kernel's one shape `{error: <sentence>, reason: <code>, hint?}`, so branch on `reason`: `limit`, `not_allowed`, `grant_failed`, `not_found`, `bad_arg`, `missing_arg` and `no_root`. A `limit` refusal also carries `scope`, `role`, `running`, `max` and, for a subtree or request limit, `lead`.
