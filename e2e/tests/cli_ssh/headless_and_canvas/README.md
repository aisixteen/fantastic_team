# cli_ssh/headless_and_canvas

The ssh twin of `cli/headless_and_canvas` (#242, #252): one task split across the local kernel (the master) and a remote one in a Podman box, wired the weak way.

The local kernel serves `canvas --port P`, the remote runs `--headless`. `rlead` (a backend on the master, made before the task) is asked by the remote agent: it makes a canvas on the remote kernel (`create_agent` of a `canvas_page` through the bridge) and adds its note in the box's clone; the lead adds a note locally. Then the local kernel is restarted as `webui --port P2`, the lead starts the remote again and makes the bridge again, and finally deletes the canvas it made there.

Checks: The box listens on sshd and the tunnel's port only; the local kernel on its page's port and the tunnel's local end only; the canvas's socket (`canvas_ws` -> `user.forward` -> the bridge) and the team page's socket list the canvas on the remote; both notes on the git server; then the local test's last checks (`webui` with `canvas` refused, `--headless` opens no port).

The team page's socket in this folder: `/team_ws/ws` is answered by `canvas_ws` here (both legs are recorded once `canvas` and then `webui` ran in one folder, and the second mount of the one route wins, `crates/team/src/webui.rs:10-12`), so the call goes through `user.forward` as the canvas page's does.

The wiring (`helpers/ssh_twins.py`): the lead's exec agent `start`s `ssh -L N:127.0.0.1:N` with the remote kernel in that session, one raw `ssh ... fantastic_team send` makes the remote `web` host, its `web_ws` leg `remote_ws`, the edges, the remote exec agent (it may call the master's agents, `<master guid>|*`, send/watch/status/stop) and the remote work program `w/work.py` (fantastic's exec_bridge connector and a small program), `git clone` runs in the box, and a local `ws_bridge` agent `remote` dials the tunnel and says `hello` with the master's guid (fantastic#476). THE BACKENDS ARE ON THE MASTER ONLY, and so is the model's key: the box holds tools and no AI agent. A remote agent that wants a model sends the master's backend its work with `send` and `watch`es it, `<master guid>|<backend>`, over that one connection (the work program, a job of the box's exec agent); the backend's turn runs on the master, its `status`, `part_*` and `done` events come back to the box as the bridge's `event` frames, and its tools are the box's exec agent, through the bridge's `forward`. The master's bridge leg is open and granted exactly send/watch/status/stop on those backends (its `can_call`, and each backend's `callable_by`). At the end: the bridge deleted, SIGTERM to the remote kernel over ssh (the tunnel closes with it).

Shared checks (`Box.end`): solved on the test's git server with one commit from each side (found in each clone's reflog), linear history; the bridge gone, the tunnel's port refusing, no exec job running; the remote kernel stopped, and, started once more, holding its stock, the surface and the exec agent only: no backend (no `*_backend` record), no spawned agent, no orphan; no model key in the box's home, its login environment or its container; the work program's arrival log shows `status` and `part_*` before `done` (the stream crossed the bridge; the check refuses an unwatched stream, a refused grant, parts only after `done`, no part); the container removed.

Needs Podman with a running machine (else `SKIP`), builds the Linux binary once per source tree (`helpers/podman_remote.py`). Free: the scripted plug (`script.json`, written by `python3 -m helpers.ssh_twins --write` in `e2e/`), the fake forge, no network.
