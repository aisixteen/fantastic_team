# cli_ssh/git_credentials

The git credentials twin of the ssh twins (#253, after #252): the remote box gets the git server's token **through the kernel bridge, from the master's credential store, per operation**, and never stores it.

The master's credential store `git_credentials` holds the token as one ref (`git/forge`), bound to the git server's host; its `env` backend keeps no value at rest, and only the bridge's leg may `get` from it (the store's `callable_by`, the bridge's `can_call`). The box has **no** token: no store with it, nothing in an environment variable, a file or a git config, from start to end (the box's own `.gitconfig` is not written, the master's sandbox has none either). The git connector (`team_git.tools`) runs on the REMOTE kernel, and its `credentials` name the master's store as `<master guid>|git_credentials` plus the ref: each `fetch` and `push` reads the token over the bridge (`get`; the value is in the reply and nowhere a kernel keeps), gives it to git only through the child's environment and the one-shot credential helper, and drops it. Nothing new in the product: `key_reader` sends `get` to the store it is given, and an id `<guid>|<store>` is routed by the kernel over the leg.

Three messages to the lead:

1. Setup: the box, the tunnel, the remote kernel and its surface, the box's repository (`git init`, the git server as `origin`: the connector has no clone verb, its `fetch` brings the objects), the bridge (its leg may `get` from the store and do nothing else there), the git connector on the remote kernel naming the master's store. Then the operator subscribes to both kernels' state streams (a `state_subscribe` through a web leg on the master, and through a tunnel of the harness's own to the remote's leg).
2. The work, on the remote: `fetch`, a worktree of `origin/main`, the fix to `muler.py`, `commit`, `fetch`, `push` of the work branch `work/muler`. It lands on the git server (checked there: one commit on top of main, main untouched, the connector's author). Then the guard: the token, in any encoding, is in neither kernel's replies, errors, state stream, records, store dump, logs or files, nor in the box's files, environments (a login's and the live remote kernel's), git configuration or container (the master's own store excepted: the kernel's environment). The state-stream taps must have seen the store's `get`, so their silence about the token means something.
3. The grant revoked (the store's `callable_by` without the leg): a push over the open bridge is refused, naming the store and the ref; the grant given back: the same push lands (`work/revoked`); the bridge deleted: a push by the box's own `send` over ssh is refused ("no agent `<guid>|git_credentials`"); the remote stopped. The master's store was read once per operation that reached it (2 fetches, 2 pushes), the git server saw exactly two authorized pushes, and the guard runs again after the run.

The mutations (the guard must fail on them): the token written into the box's git config as an `extraHeader` (what the other twins do, and what skipping the bridge would need), and the token form-encoded in a file of the master's run folder.

The box reaches the git server on its own `127.0.0.1` (a relay, a job of the box, carries the bytes to Podman's gateway): the connector sends a credential only over https or over http to loopback, and the box dials the server through the gateway, which is not loopback. The relay is the stand-in for the TLS a real forge has.

The wiring and the shared checks are `helpers/ssh_twins.py`'s (`git_box_command`, `remote_git_record`, `script_git_credentials`, `secret_forms`, `leaks`, `Box.guard_box`). Needs Podman with a running machine (else `SKIP`). Free: the scripted plug, the fake forge, no network.
